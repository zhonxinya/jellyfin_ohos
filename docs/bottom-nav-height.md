# 底部导航栏高度一致性（系统导航条区域）

> 面向：验收与后续迭代。记录**问题现象**、**实测数据**、**为什么这么改**与**设备实测证据**。
> 相关代码：`pages/MainShell.ets`（`applyChromeForTab` / 底部页签行）、
> `components/AppTopBar.ets` + `components/PageHeader.ets`（沉浸式下的挖孔避让）、
> `common/WindowFullscreen.ets`（`styleNavigationBarWith` / `exit(win, color)`）。
>
> 本文件记录**两轮**改动：第一轮（PR #54）把页签行下面的异色横带铺成应用底色；
> 第二轮（PR #56）让页签行真正落到屏幕底边并与「视频」页对齐。

---

## 一、问题现象

底部页签行看起来"高度不一致"：

- 「媒体库」「设置」页：页签行下面挂着一条**浅色（模拟器上纯白）横带**；
- 「视频」页（沉浸式）：同一位置是应用的深色底，页签行直接顶到屏幕底边。

两处拼在一起，同一个页签行一处"矮一截"、一处"齐到底"。
第二轮把口径定为：**页签行必须落在屏幕底边、与「视频」页同一位置**。

## 二、实测数据（模拟器 127.0.0.1:5555，1260×2844 px，密度 3.375）

`uitest dumpLayout` + `snapshot_display` 截图逐行取色：

| 页签 | 应用内容区（root 内缩） | 底部页签行 Row | 行高 | 页签行下面那一带 |
|---|---|---|---|---|
| 媒体库 | `[0,132][1260,2750]` | `[0,2561][1260,2750]` | 189px = **56vp** | y=2750..2843 **纯白**（94px = 27.9vp） |
| 设置 | 同上 | 同上 | 同上 | 同上 |
| 视频（沉浸式） | `[0,0][1260,2844]` | `[0,2655][1260,2844]` | 同上 | 无（行本身就是最后一行） |

三条硬事实：

1. **页签行本身的高度三个页签完全一致（56vp）**，图标 74px、文字 40px、间距与内边距也逐像素相同 ——
   所以"高度不一致"不是 `TAB_BAR_HEIGHT` 的问题，而是**页签行下面多出来的那一条**（第一轮）
   以及**页签行的屏幕位置差了一个系统导航条**（第二轮）。
2. 那 94px 正好是 `WindowManagerService` 里 `SCBGestureNavBar` 的 bounds（`[0,2750][1260,94]`）。
3. 应用窗口**本来就是整屏**（`WindowRect = [0,0,1260,2844]`），系统导航条底色回读为
   `#00FFFFFF`（全透明）—— 那一条之所以是白的，是因为**应用没有往窗口安全区以外的底部区域画东西**，
   露出的正是系统底（浅色模式下为纯白）。

补充探针（用来排除"改系统栏颜色就行"这条弯路）：`setWindowSystemBarProperties({navigationBarColor})`
调用成功且 `getWindowSystemBarProperties()` 回读为设置值（实测写入 `#FFFF00FF` 也回读到了），
但那条 `SCBGestureNavBar` 仍照原色绘制 —— 该窗口模式下系统导航条的底色不接受应用指定
（`#00FFFFFF` 本来就是"让应用自己画"的语义）。

## 三、改法（两轮）

### 第一轮：把页签行下面的异色横带铺成应用底色

1. **外壳根容器把页面底色铺到屏幕底边**：最外层 `Column` 用底部页签行的底色（`cardBackground`）
   + `expandSafeArea([SafeAreaType.SYSTEM], [SafeAreaEdge.BOTTOM])`（只影响绘制，不改布局）。
2. **系统导航条颜色跟着主题走**（`WindowFullscreen.styleNavigationBarWith`）：兜底用。
   在系统导航条**不透明**的机型/窗口模式下，至少让它的颜色与应用一致，不再出现异色横带。
3. 没有动 `TAB_BAR_HEIGHT`、也没有增加底部内边距。

> 第一轮的 `expandSafeArea` 在第二轮被移除：那时内容区还没铺满，需要它把底色画进安全区；
> 现在内容区本身就是整屏，根容器的底色自然盖到底边。

### 第二轮：页签行真正落到屏幕底边（三个页签统一整屏沉浸式）

**关键约束（实测）**：应用只能在**自身内容框**内接收点击，内容框外的部分**画得出来但点不动**。

- 非沉浸式窗口的内容框被系统按可见系统栏内缩（模拟器实测底部少 94px），页签行停在 y=2750；
- 用负下边距把它推到 `y=2656..2844`（视觉到位了）：从**非沉浸式**页签点它的下半部分**完全无响应**，
  从**沉浸式**的「视频」页点同一位置则正常；单独再关掉系统导航条也一样 —— 那是应用自己的裁剪；
- `ignoreLayoutSafeArea(BOTTOM)` 试过：整块内容被在"长高后"的盒子里居中下移 47px，
  顶栏跟着掉 46px，页签行仍差 47px 到不了底。

因此唯一可行解是**让窗口内容区铺满整屏**。两条路都验过：

| 方案 | 结果 |
|---|---|
| 铺满 + **保留状态栏**（只让系统导航条让位） | ✗ 平台会把**外壳顶栏压扁**：190px → 59px（`dumpLayout` 里顶栏 Row 只剩 57px、标题 Text 2px；截图像素里标题完全不可见）。`flexShrink(0)`、`constraintSize({minHeight})`、在页面内容列最前面插一个 0 高度垫片**都挡不住**；把状态栏一起隐藏时一切正常 |
| 铺满 + **隐藏状态栏与导航条**（= 「视频」页那套） | ✓ 三个页签统一整屏沉浸，页签行贴屏幕底边且整行可点（本轮采用） |

**本轮改动**：

1. `MainShell.applyChromeForTab`：三个页签**都**走 `WindowFullscreen.enter()`（隐藏两条系统栏 +
   铺满整屏），不再按页签区分；去掉了"状态没变就跳过"的提前返回 —— 播放页/详情页会自己进出沉浸式，
   它们改的是同一个窗口，跳过会让窗口停在别人留下的状态上。
2. 沉浸式下系统不再替应用避让顶部，**挖孔（刘海/胶囊）由应用自己躲**：
   外壳把 `WindowFullscreen.insets(win, false).top` 写进 `AppStorage['shellTopInsetVp']`，
   `AppTopBar` / `PageHeader` 用 `@StorageProp` 读它做顶部内缩（两处覆盖外壳与近 40 个压栈页面）。
   键在 `aboutToAppear` 里**先建出来** —— `@StorageProp` 只在键已存在时才会收到后续更新（踩过一次）。
3. `MainShell.aboutToDisappear`：还原窗口（`WindowFullscreen.exit`）并把该键清 0 ——
   沉浸式是窗口级状态，退出登录后服务器配置/登录页并不走本外壳，得有人替它们收拾。
4. 移除根容器的 `expandSafeArea`（内容区已是整屏，不再需要）。

## 五、已知限制

- **媒体库 / 设置页现在也不再显示系统状态栏**（时钟、电量）：这是上面那条平台限制的直接后果 ——
  "铺满 + 保留状态栏"会被平台压扁顶栏，只能二选一。三个页签与「视频」页从此行为一致。
- 挖孔避让的**非零路径未在真机验证**：模拟器无挖孔，下发的真实值是 0；
  机制本身用强制 39vp 的探针验证过（顶栏内容内缩 132px）。
- 系统手势提示条的**颜色/显隐**由系统决定，应用无法移除；现在它压在页签行上
  （与「视频」页同款表现）。
- 只覆盖手机竖屏；折叠屏/平板的系统导航条形态（例如 2in1 的底部任务栏）未在本机验证。
