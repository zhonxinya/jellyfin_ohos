# 短视频模式（「视频」导航页）

> 面向：验收与后续迭代。记录**已交付行为**、**视觉与交互规格**、**取数/播放策略**、
> **实测证据**与**已知限制**。
> 相关代码：`pages/ShortVideoPage.ets`、`pages/settings/ShortVideoSettingsPage.ets`、
> `common/ShortVideoPrefs.ets`、`pages/MainShell.ets`（页签与外壳顶栏）、
> `components/JellyfinImage.ets`（`fillMode`）。

---

## 一、它是什么

底部导航新增一个**「视频」页**（媒体库 / **视频** / 设置，抽屉里也有入口），承载**短视频模式**：
把用户在设置里勾选的若干**媒体库**当成"短视频源"，随机抽条目、竖屏满屏逐条连播。

为什么单独做一个导航页，而不是塞进媒体库页：「短视频」的心智是**打开就刷**，
与"进库 → 找片子 → 进详情 → 播放"是两条完全不同的动线；混在一起两侧都会变复杂。

## 二、怎么用

1. **设置 → 播放 → 短视频模式**：
   - 列出服务器上的媒体库（标注集合类型；对"通常不含视频"的库如实提醒），**勾选即保存**
     （开关类设置不设保存按钮），该行副标题显示「已选 N 个媒体库」；
   - **清晰度（服务器转码）**：单选档位，决定"直连还是服务端转码、码率多少"（见第四节）；
2. 打开底部**「视频」页**：随机流立刻开始播；**上滑**切下一条，**播完自动下一条**；
   **电视剧只作为"一个作品"出现一条**（代表它的是按播放历史算出的那一集，见第五节）；
3. **单击画面**：控件已可见时 = 暂停 / 继续（中央出现「已暂停」提示）；
   **控件已自动隐藏时 = 只把控件唤出来，不改播放状态**（见第八节）；
4. **双击画面左/右两侧**：快退 / 快进 10 秒（画面中央短暂提示「快进 10 秒」）；
   双击不含暂停，控件藏没藏都一样；
5. **右侧操作栏**（竖排四个按钮，图标 + 文字）：**收藏**、**标记已看**、**详情**、**换一批**；
   收藏/已看是**服务端状态**（`UserData`），操作结果用 toast 反馈、按钮文案同步变化；
6. **左上角工具行**：`短视频` + 页码 `3/48` + **清晰度徽标**（`设置 · 实际方式`，如 `720p · 转码`）
   + `来自：库A / 库B`；右侧是**方向**（跟随系统 / 横屏 / 竖屏）、**全屏**（横屏 + 页签栏让位，见第七节）与**设置**入口；
7. 底部细进度线 + `已看 / 总时长`；本条播不了时给「去播放页 / 跳过」并倒计时自动跳过。
8. **播放中 4 秒无交互，上下控件会自动隐藏**（画面优先）；点一下画面或滑动即可唤回。
   控件隐藏时的**第一下点按只唤出控件**、不暂停（见第八节）。

## 三、视觉规格（本轮美化）

关键改动：**画面铺满整屏，控件做成压在画面上的浮层**（而不是"顶栏 + 工具行 + 一小块画面"）。

| 项 | 做法 | 为什么 |
|---|---|---|
| 外壳顶栏 | 「视频」页签下**不画** `MainShell` 的 `AppTopBar` | 顶栏 56vp 是从画面里直接扣掉的（竖屏手机上接近可见高度的 1/10）；抽屉/搜索在这条动线上用不上，底部页签仍可切走 |
| 顶部工具行 | 浮层 + 顶部渐变 scrim（`120vp + 挖孔内缩`） | 文字在亮画面上也可读，同时不占用画面高度 |
| 环境背景 | 当前封面**铺满 + `scrim` 压暗**，垫在**视频面之下** | 竖屏是 20:9 窄长屏，横片按"适应"缩放后四周本来是两条纯黑边；垫上同图的暗色放大版后是一整块画面（Plex/Infuse 同款处理）。**设备实测**：`scrimHeavy`（80% 黑）下留白区亮度只有 13/255，肉眼仍是一条黑边；改用 `scrim`（53%）后同一区域 33~59/255，结构清晰可见 |
| 底部信息 | 类型徽标（品牌色实底 + `onBrand`）+ 系列名 + 标题（≤2 行，20fp）+ 元信息（年 · 评分 · 时长 · 类型，≤1 行）+ 简介（≤2 行） | 短视频的"这一条是什么"必须一眼看清；此前是"标题 + 元信息 + 两个大按钮 + 页码"挤在一行。简介经 `stripMarkup()` 去掉 HTML（实测有 B 站视频简介带 `<a href=…>` 标签） |
| 右侧操作栏 | 圆形浮层按钮 46vp + 11fp 文字标签，选中态用品牌色实底 | 常用动作收进单手可及的位置；此前「详情/重播」两个大按钮横排在文字旁边 |
| 底部进度 | 3vp 细线 + `mm:ss / mm:ss` | 能看出"还剩多少"。总时长**播放器拿不到时回退元数据**（`RunTimeTicks`）：设备实测部分流在 `prepared` 阶段 `AVPlayer.duration` 仍为 0，只信播放器的话进度线恒为 0、读数根本不出现 |
| 中央状态 | 「正在准备…」转圈 / 「已暂停」大播放图标 / 双击跳转提示 | 切换条目时不再是"黑一下"；暂停与手势有明确反馈 |

## 四、清晰度与服务器转码（本轮新增）

**为什么要有这个设置**：短视频是移动网络下最吃流量的用法，用户需要"别给我放原盘"的开关；
而服务端转码也是"本机解不了的编码"（AV1 等）**唯一能硬解播放**的途径。

档位（`common/ShortVideoPrefs.ets` 的 `kShortVideoQualities`，存偏好 `shortVideoQuality`）：

| 档位 | 请求参数 | 实际行为 |
|---|---|---|
| 自动（默认） | 直连优先 + 带 `DeviceProfile` | 服务端能直连就直连；本机不支持的编码由服务端转码（HLS），交给系统硬解 |
| 原画直连 | `includeDeviceProfile=false`、`enableTranscoding=false` | 只给直连地址；本机解不了的编码退回**本机软解** |
| 1080p / 720p / 480p / 360p | `maxStreamingBitrate` + `enableDirectPlay=false` + `enableDirectStream=false` | **强制服务端转码**到该清晰度（10 / 4 / 1.5 Mbps / 720 Kbps） |

播放参数由 `ShortVideoPrefs.playbackOptionsJson()` 生成，`ShortVideoPage.playCurrent()` 交给
`JellyfinPlayer.playerOpen(itemId, options)`；原生侧同一条 `PlaybackInfo` + 策略解析路径会优先用
`MediaSource.TranscodingUrl`（见 `native/core/api/playback_resolve.cpp`）。

**软解必须强制直连**（`directOptionsJson()`）：本工程的 FFmpeg 是 `--disable-network` 构建，
取流由宿主按 Range 取字节，**打不开 HLS（.m3u8 + 分片）**。软解若仍带 `DeviceProfile`，
服务端会为"本机不支持的编码"返回转码地址，软解拿到 m3u8 只有失败一条路（表现为"这条播不了"）。

**转码流失败要能回退**：服务端转码本身可能失败（ffmpeg 起不来 / 分片 500）。因此
`onItemFailed` 里有一条**换条路再试一次**的规则（每条内容只用一次，`retryTried`）：

| 刚失败的是 | 换到 | 为什么 |
|---|---|---|
| 服务端转码流 | 直连 | 转码任务本身可能起不来，直连往往还能放（本机硬解或软解都行） |
| 直连且档位是**「自动」** | **服务端转码（让服务器解码）** | 直连走的是**本机硬解**，解不了就是解不了 —— 交给服务端转成 H.264/AAC 后走硬解，比本机 FFmpeg 软解省电，而且软解路径**没有音频输出** |
| 直连且档位是「原画直连」 | （不换，直接软解） | 用户明确选了"不请求转码、解不了走本机软解"，不该偷偷改成转码 |

换路之后仍失败才落到**本机软解 → 提示 + 自动跳过**。

### 「自动」档为什么要先让服务器解码（本轮修复）

直连流是**本机硬解**。实测踩到的典型是"视频没问题、音轨解不了"：
`城市猎人`（视频 **h264** / 音轨 **DTS 6ch**）被服务端判为**直连**（设备能力表按 FFmpeg
解码器列表声明了 `dts`，服务端认为这台机器能放），而系统 AVPlayer 解不了 DTS ——
于是硬解失败。旧行为在这一步**直接跳过这一条**（用户看到"这条播不了"一闪而过），
新行为先改走"强制服务端转码"：服务器把音视频都转成客户端真能解的编码，播放继续。

实测数据（模拟器 127.0.0.1:5555，库「华语电影」467 条）：

| 项 | 值 |
|---|---|
| 含 dts / truehd / mlp / pcm_* 音轨 | **102 条**（22%） |
| 其中视频是 h264（服务端会判直连） | **56 条**（12%） |
| 视频是 hevc 且容器是 mp4/mov（同样判直连） | 也会命中同一条修复路径（见下方日志） |

> 根因仍在**设备能力表**：`native/core/api/device_profile.cpp` 的 `audioCodecs` 是按本工程
> FFmpeg 的解码器列表写的（含 dts/truehd/mlp/pcm_*），而系统 AVPlayer（直连那条路）并不都支持。
> 本轮不去动那张表（它同时影响播放页与所有直连场景，且"真机能不能解 DTS"没有实测依据），
> 而是把兜底策略改成"先让服务器解码"。

**设备实测（模拟器 127.0.0.1:5555，`_sv-autodecode-verify.py`）**

两条真实链路（日志原文，`hilog -x | grep -E 'JellyfinShortVideo|SoftPlay'`）：

```
# ① 看门狗判失败（直连一直不出画面）
playCurrent item=db2ab3c8… quality=自动
SoftPlay: playerOpen method=DirectPlay codec=hevc container=mov profileFallback=0
onItemFailed method=DirectPlay msg=这条内容迟迟没能起播
直连本机解不了，改由服务端解码（强制转码）再试一次
SoftPlay: playerOpen method=Transcode codec=hevc container=mov
reopen method=Transcode hls=1

# ② 硬解直接报错
playCurrent item=c58e4ea9… quality=自动
playCurrent method=DirectPlay hls=0
onItemFailed method=DirectPlay msg=本机无法播放该内容（可能是硬解不支持）
直连本机解不了，改由服务端解码（强制转码）再试一次
reopen method=Transcode hls=1
```

顺序与预期一致：**直连（本机硬解）→ 失败 → 服务端解码（强制转码）→ 转码流起播**，
两次都没有落到本机软解（原生 `SoftPlay` 里没有软解会话，只有 `playerOpen` 两条）。

对照（改动前，同一个库、同一档位）：`城市猎人`（h264 + DTS）直连失败后**直接跳到了下一条**，
既没有请求服务端转码、也没有软解 —— 用户看到的是"这条播不了"一闪而过。

**播放方式要如实上报**：进度上报的 `PlayMethod` 曾经写死 `DirectStream`，
于是"服务端转码播放"在服务端那边看不出是转码（设备实测：客户端日志 `method=Transcode hls=1`，
而 `/Sessions` 仍报 `DirectStream`、`TranscodingInfo` 为空）。现在原生侧记录本次解析出的方式
（`CurrentPlayMethod`）并随进度上报 —— 修复后设备实测 `/Sessions` 报
`PlayMethod=Transcode`，`TranscodingInfo{video=h264, bitrate=3.76Mbps, 1920x1080}`（720p 档位）。


## 五、取数策略（为什么这样取）

| 决策 | 原因 |
|---|---|
| 逐库取（`ParentId` 单库） | Jellyfin `/Items` 只接受单个父级；逐库取还能**隔离失败** —— 一个库挂了不影响其它库出内容 |
| `includeItemTypes=Movie,Episode,Video,MusicVideo` | 短视频只关心"能直接播的视频类条目" |
| **同一部剧只留一条**（`collapseSeries`） | 一部 40 集的剧平铺会占掉 40 个位置，"刷内容"变成"刷同一部剧的不同集"（见第四节之二） |
| `SortBy=Random` + 本地 Fisher–Yates | 服务端随机避免"总是同几首"，本地再洗一次避免"总是先放第一个库的内容" |
| 全空时区分"没内容"与"取数失败" | 两者该给的动作不同：**换库** vs **重试** |
| 偏好存 `shortVideoLibraries`（媒体库 **id** 列表） | 名称会随服务端改名/多语言变化，id 才稳定；服务端已删除的库在进设置页时自动剔除 |
| `Fields` 只多要卡片上真的会显示的字段（`OfficialRating,Genres,SeriesName,SeriesId`） | 字段少要 → 分级/类型徽标只能是空白；多要 → 响应变大 |

### 电视剧作为一个作品（本轮新增）

短视频列表里**一部剧只出现一条**，代表它的是"**按播放历史算出的那一集**"。

**选集完全交给服务端**：`/Shows/NextUp?SeriesId=<剧集id>&Limit=1`
（原生新增 `getNextUpForSeries`）。服务端语义（源码
`Emby.Server.Implementations/TV/TVSeriesManager.cs`）：

| 观看状态 | NextUp 返回 |
|---|---|
| 看过前面几集 | **接着看的那一集** |
| 一集都没看过 | **第一集**（第 151 行 `alwaysEnableFirstEpisode` 的兜底；`SeriesId` 存在时 `limit=1`） |
| 全看完了 | **空** → 这条剧**不进列表**（没有"下一集"可刷） |

这样"按播放历史确定集数"由服务端既有语义保证，客户端不用自己推导季/集顺序。

**客户端只做三件事**：

1. **折叠**：`SeriesId`（或剧名兜底）相同的条目收成一条（`collapseSeries`）。
   同一批内只出一条；**追加**时还会跳过列表里已有的剧，**「换一批」不跳过**
   —— 否则会把眼下正在显示的剧全部剔除。
2. **合成展示条目**（`asSeriesEntry`）：`id` 用那一集（播放/收藏作用在具体一集），
   `seriesId` 记住原本是哪部剧；**展示信息一律取剧**（标题=剧名、图片/简介/年份/分级/类型=剧），
   时长与进度取那一集（进度线要如实反映接着看的位置）。
3. **分流「详情」**：折叠条目点「详情」进**剧集**详情页（`detailId()`），
   进某一集的详情页会把用户锁死在那一集。

界面口径：「类型徽标」显示**剧集**（不是"单集"）、标题是**剧名**、下面单独一行「第 N 季 第 N 集」。
`displayTitle()` 对这类条目**不加 `E{n}` 前缀** —— 否则标题 `E1 洛基` 与标签 `第 1 季 第 1 集`
会把同一信息说两遍，且 `E1` 这种写法对用户不友好（设备实测踩到）。

**实测证据（模拟器 + Jellyfin 10.8.12）**

| 判定 | 结果 |
|---|---|
| 折叠生效 | 一次取数 11 部剧各出一条；日志逐条 `series collapse key=…「X」→ episode=… E n` |
| 界面上是"作品" | 「剧集」徽标 + 剧名（如 `老友记`）+ `第 1 季 第 1 集` 一行 |
| 未看过的剧 | 全部定位到 E1（与 NextUp 语义一致） |
| **有播放历史时定位正确** | `路西法` S1E1 `Played=True` → 该剧定位到 **E2**（`c145b2e2…`，服务端 `/Shows/NextUp` 独立复核同为 E2） |
| 详情分流 | 点「详情」进入**剧集**详情页（页面显示「剧集」徽标与「播放本集」） |
| 全部看完的剧被剔除 | 日志 `series drop（无下一集）key=… name=野火` |
| 「换一批」仍出满一批 | 两次取数分别 11 部 / 9 部剧，不是空列表 |

**已知取舍**

- 每部剧多一次 NextUp 请求。**这些请求已改为有界并发**（`kSeriesConcurrency = 6`，
  见「首屏取数的并行化」一节）—— 串行发会让首屏付十几倍往返，正是"第一次加载慢"的主因。
  在凑够 `kAppendAhead` 部剧时才向队列尾部追加，追加本身也不在首屏路径上。
- 只按**剧集归属**折叠；`Movie`/`Video`/`MusicVideo` 各自仍是一条（它们没有"下一集"的概念）。
- 该服务器的剧集条目 **`SeriesId` 为空**（只有 `SeriesName`），因此折叠 key 与 NextUp 参数
  以 `SeriesId` 为空为界退化为"按剧名取第一集"（拿不到播放历史，但至少能播、仍是一条剧）。


### 无限流（本轮新增）

- 滑到**距末尾 4 条**时后台预取下一批（`prefetchIfNearEnd`），滑到底不会出现"空白等待"；
- 取到的条目按 id **跨批去重**（`collectBatch(libraryIds, true)`）—— 否则服务端随机
  会把看过的那几条再塞回来，"刷不完"就变成"反复刷同几条"；
- 真的取不到新内容才置 `exhausted`，并在末尾给「这批已经看完了 / 换一批 / 设置」；
- **「换一批」不去重**（`collectBatch(libraryIds, false)`）：它要的是"再来一批新的随机内容"，
  若把已刷过的都排除掉，刷得越多可换的越少；
- 追加是异步的：`feedGeneration` 代次校验保证「换一批」之后不会被上一代的追加结果污染。

## 六、横屏 / 竖屏

**入口**：工具行右侧的「方向」按钮，循环切换 `跟随系统 → 横屏 → 竖屏 → 跟随系统`（图标 + 文案，
一眼可见当前处于哪一档）。用播放页同一套 `WindowFullscreen.setOrientation`，不另起一套平台调用。

**选择会被记住**（偏好 `shortVideoOrientation`）：横竖屏是"躺着看 / 坐着看"的选择，
不该每次进应用重新点一次。偏好值异常时回落 `auto`（不让坏数据把窗口锁在奇怪的方向）。

**离开页签会还原**：方向是**窗口级**状态，而本页是嵌入式组件 —— 用户在「视频」页选了横屏，
切到「媒体库 / 设置」后那些页面并没有横屏布局。因此 `onTabIndexChanged` 里
"离开即还原（`restoreOrientationOnLeave`）、回来即重新应用"，成对进出（与播放页同一套做法）。

**横屏要单独排版（不是把竖屏的量缩一缩）**：横屏可用高度只剩 ~306vp（2844×1071px 画面区），
而竖排的四个操作按钮约 270vp —— 设备实测**收藏按钮与「设置」「方向」重叠 85×108px**
（点哪个都可能点错）。因此横屏改成：

| 项 | 竖屏 | 横屏（`this.landscape`） |
|---|---|---|
| 操作栏 | 右侧**竖排**一列（46vp 圆钮 + 文字） | 右下角**横排**一行（40vp 圆钮 + 文字） |
| 信息区 | 与操作栏并排，标题 ≤2 行、简介 ≤2 行 | 占左侧，标题 ≤1 行、简介 ≤1 行（19fp/13fp） |
| 触摸"控件区"判定 | 顶部 64 + 底部 108 + 右侧 84×380 | 顶部 64 + 整条底部 92（`kLandscapeBottomVp`） |

> 判定区必须跟着布局走：竖屏那套"右侧一列 84×380"用在横屏会把大半个画面判成控件区，
> 于是"点画面暂停"在横屏右半边完全失效。

## 七、主动全屏（横屏 + 底部页签栏让位）

**入口**：工具行右侧、「方向」与「设置」之间的那个图标按钮（展开 ⤢ / 收起 ⤡）。

**它解决什么**：进「视频」页本来就是沉浸式（外壳隐藏系统状态栏与导航栏），但那是**被动默认态** ——
底部仍留着外壳的 56vp 页签栏，画面只占 2655/2844px（93.3%）。主动全屏是用户按一下：
**转横屏 + 页签栏整条收起**，画面真正铺满整屏；再按一下回到进全屏之前的样子。

**为什么"横屏"和"铺满"要一起做**：竖屏是 20:9 的窄长屏，横片按适应缩放后上下本就是黑边，
单把页签栏收掉只多出 56vp；横过来才是画面真正"变大"的那一步（可用区域从窄长变宽屏）。
两者合起来才叫全屏 —— 这也是"点一下直接横屏铺满"这个口径的由来。

| 项 | 行为 |
|---|---|
| 进入 | 记住当前方向偏好 → 切 `landscape` → 外壳收起底部页签栏；同时把控件亮出来（用户要能看到"怎么退出去"），随后照旧 4 秒自动隐藏 |
| 退出 | 方向**还原成进全屏之前的选择**（不是固定回"跟随系统"：用户本来锁着「竖屏」，出去仍是「竖屏」）→ 页签栏回来 |
| 退出入口 | 再点同一个按钮（画面上点一下即可唤出控件；暂停时控件常驻） |
| 与「方向」按钮的关系 | 全屏中把方向切成非横屏（竖屏/跟随系统）→ **自动退出全屏**，否则会出现"竖屏 + 页签栏消失"的自相矛盾态，用户连别的页签都切不回去 |
| 离开页签 / 页面销毁 | 一律收回全屏状态（页签栏是唯一的页签入口，不能让它消失） |
| 持久化 | **不持久化**（每次进「视频」页都是非全屏）。页签栏是唯一入口，启动就消失会把人锁在视频页 |
| 全屏中的「详情」/「设置」 | 照常可用；从这些子页返回仍是全屏（`onPageShow` 后状态保持） |

**实现要点**

- 页签栏是**外壳**画的（`MainShell` 的底部 `Row`），页面自己藏不掉 —— 因此
  `ShortVideoPage.fullscreenActive` 是 `@Link`，页面写、外壳读，外壳用 `if` 决定画不画那一条。
  **用 `if` 而不是 `opacity(0)`**：透明的页签按钮仍然可点，"藏起来却还吃触摸"是本项目踩过的一类 bug。
- 页签栏收起后 `Tabs`（`layoutWeight(1)`）自然拿到那 56vp，画面随之铺满 —— 没有任何额外的尺寸计算。
- 外壳侧另有一道兜底：`applyChromeForTab` 发现当前不在「视频」页签时强制 `videoFullscreen = false`。

**系统手势提示条（实测结论）**：页签栏收起后本页底部第一次直接落在屏幕底边，那一条上系统还会画手势提示条。
进全屏时探针打印 `TYPE_NAVIGATION_INDICATOR`：**visible=1 但 bottomRect.height=0**（`TYPE_SYSTEM` 同样为 0）——
沉浸式下系统把避让区尺寸清零，"可见"并不带尺寸，因此页面量到的让位高度**恒为 0**。
好在模拟器横屏全屏下截图逐行扫描**未见提示条绘制**，底部进度线（3vp，屏底）也没有被压住，不存在重叠。
代码里保留了这次测量（真机手势导航若报出真实高度，底部会自动让开）。

### 首屏取数的并行化（本轮修复「第一次加载慢」）

**症状与根因**：打开「视频」页第一次要等很久。根因不在服务端算得慢（单个请求
服务端只花 0.1~1s），而在**往返次数**——本工程 `HttpClient` 每次请求都新建一条 TCP 连接
（`http_client.h` 原话“keep-alive is never used”），而旧实现在两处**逐项串行等待**：

| 旧行为 | 代价 |
|---|---|
| 逐媒体库取条目（`for` + `await`） | N 个库就付 N 倍往返 |
| 逐剧集问 NextUp（`collapseSeries` 里 `await`） | 一批十几部剧付十几倍往返（**首屏最大的一块**） |
| 先 `await` 取库名、再去取内容 | 白给首屏多一次往返（库名只是工具行那行文字） |

**改法**：新增 `common/Parallel.ets`（有界并发 map，按输入顺序返回、单项失败记为 `null`），
把上面三处改成并发：

- `kLibraryConcurrency = 4`：逐库取条目的并发上限（用户可能勾十几个库）；
- `kSeriesConcurrency = 6`：逐剧 NextUp 的并发上限；
- 库名改为**后台**刷新（`refreshLibraryNames`，带“配置没变才写回”的代次校验）。

`collapseSeries` 相应改成三段：**① 定槽位**（同步决定哪些条目直接保留、哪些要问 NextUp）
→ **② 并发解析** → **③ 按槽位顺序组装**。输出顺序仍等于“条目在服务端响应里的顺序”，
去重语义与串行版逐条一致（`pushIfNew` / `hasSeries` 不变）。

**为什么并发是有界的**：每请求新建一条 TCP 连接，全开就是连接风暴。实测
（模拟器 + 真实服务器，同一库反复请求）6/8/12/16 并发**失败率全为 0**，因此 4 与 6
是“收益已到位、风险可控”的取值。

**实测对照**（判据 = 应用 hilog 的 `loadFeed batch=` / `collapseSeries` / `playerOpen`）

| 场景 | 取数段（batch） | 其中逐剧 NextUp | 到起播（feed start） |
|---|---|---|---|
| 本机 LAN，串行（改前） | 507ms | 225ms（22 部剧） | 887ms |
| 本机 LAN，并发（改后） | 486ms | 184ms（21 部剧） | 1114ms |
| **+120ms/请求，串行（改前）** | **3207ms** | **2559ms**（20 部剧） | **3760ms** |
| **+120ms/请求，并发（改后）** | **1051ms** | **730ms**（18 部剧） | **1718ms** |

> 本机（模拟器与服务端同一台机器）单次往返约 1ms，把 N 倍往返完全掩盖了——
> 串行与并发都是 ~500ms，看不出差别。因此验证用了一个**注入 120ms/请求延迟的反向代理**
> （`/tmp/delayproxy.py`，仅验证用、不进仓库）把真实网络条件搬到本机；
> 地址指向该代理测量同一批内容。这才是“远程服务器 / 移动网络”下的真实差距：
> **首屏 3.76s → 1.72s（约 2.2×）**，取数段 3.21s → 1.05s（约 3.1×）。

**回归验证**（模拟器 127.0.0.1:5555，真实服务器）：冷启动进「视频」页 `1/42` 正常出内容并起播；
上滑 `1/44 → 2/44 → 3/44`；「换一批」`3/44 → 1/47`（重新取数生效）；
直连解不了时仍按既有策略改走服务端转码（`onItemFailed method=DirectPlay` →
`reopen method=Transcode hls=1`）；首次进入**只取一次数**（`loadFeed batch=` 计数 1，无重复取数）。

- **空态分两种**：没配过库 → 引导「去设置」；配过但没内容 → 提示换库或先入库内容。
- **从设置页返回必须热更新**：`ShortVideoPage` 是 Tabs 里的普通组件，从设置页返回**不会重建**
  （`aboutToAppear` 不再触发），刚勾完库回到「视频」页会仍是空态。
  做法：`MainShell.videoTabTick` → `@Prop @Watch` 信号，切到该页签时**重读配置**，
  且**只在配置真的变了**（或本来无内容）时才重新取数 —— 否则来回切页签会把正在看的那条随机掉。
- **`getHomeSection('views')` 返回的是 `/Views` 原始响应**（顶层就是 `Items`），
  不是 `{views: {...}}` 包装；用 `JsonUtil.extractItems()` 取（早期版本取错导致"没有可用媒体库"）。
- **工具行/图标**：`sys.symbol.play_rectangle` **不是**有效系统符号（编译期报
  `Unknown resource name`），视频类图标用 `sys.symbol.play_circle`。
- **取数错误不能用"出参字符串"回传**：ArkTS 的 `string` 按值传递，早先版本
  `fetchLibraryBatch(id, outError)` 里写的错误调用方**永远读不到** —— 于是"取数失败"
  被当成"库里没有内容"，该给「重试」的时候给了「去设置」。现在错误记在页面字段 `batchError` 上。
- **单击/双击必须自己判定**：同一块区域上的两个手势，如果同时挂 `onClick` 与双击手势，
  一次双击会顺手触发单击（画面先暂停一下）。做法与播放页一致：单击**延后**
  `kSingleTapDelayMs` 执行，双击到达时取消待执行的单击。
- **浮层按钮不能靠"事件冒泡"过滤**：工具行/操作栏是叠在画面上的浮层，与手势层是**兄弟节点**，
  浮层容器用 `HitTestMode.Transparent`（自身与子节点响应、不阻塞兄弟）才能点得动按钮 ——
  代价是一次点按**同时到达两者**。因此"点按钮"与"点画面"由手势层按**坐标**区分
  （`inChromeZone`：顶部 64 + 挖孔内缩、底部 108、右下操作栏 84×380），
  位置判定与事件顺序无关，比"按钮按下时打标记"可靠。
- **起播看门狗**：`AVPlayer` 有"既不进 playing、也不报 error"的静默状态（转码流起播、弱网）。
  没有看门狗时用户会一直盯着转圈且**永远不会自愈** —— 现在 15 秒没出画面就按"这条播不了"
  处理（换条路重试 → 软解 → 提示 + 自动跳过，见第四节）。
- **自动跳过要一秒一跳**：原先文案是静态的"将在 4 秒后自动跳过"，现在显示剩余秒数。
- **列表被清空时必须显式停播**：状态切到空态/错误态后视频层不再参与构建，但
  AVPlayer/软解会话不会因此停止 —— 不显式收掉的话用户会"看着错误页、听着上一条的声音"。
- **屏幕常亮**：短视频是"长时间只看不摸屏幕"的用法，此前漏了 `setWindowKeepScreenOn`，
  系统息屏时间一到画面就黑掉（观感是"看着看着断了"）；现在播放时开启、离页/切页签还原。
- **封面只画当前这一条**：`ForEach` 会为整批条目建组件，一屏只看得到一条，
  却要为每条拉一张 900px 的图（原生下载 + 解码）。现在只有当前条目画封面，
  一屏一条并发取图的问题随之消失。

## 八、上下控件的自动隐藏（画面优先）

播放中 **4 秒无交互**就把顶部工具行与底部信息/操作栏藏起来（`kChromeAutoHideMs`），
任何点按或滑动都把它们唤回来 —— 短视频是"一直在放"的场景，控件常驻既挡画面又容易误触。

| 情形 | 行为 | 为什么 |
|---|---|---|
| 播放中 4 秒无交互 | 隐藏上下控件（220ms 淡出） | 画面优先；控件是临时浮层，不是常驻栏 |
| 单击画面（**控件隐藏时**） | **只唤出控件，不改播放状态** | 这一刻用户想找的是按钮，不是在操作播放；顺着暂停的话他会看到"我点一下想找按钮、画面却停了" |
| 单击画面（**控件已可见时**） | **暂停 / 继续**，并把控件留住 | 控件已经亮着，用户看得到按钮，此时点按的意图就是切播放状态 |
| 双击画面两侧 | 快进 / 快退 10 秒（并唤出控件） | 手势结果需要可见反馈；双击路径**不含**暂停，不论控件藏没藏 |
| 滑动切条 | 新条目控件先亮出来，再重新计时 | 换条是"我想看看这条是什么"的时刻 |
| 暂停 / 正在准备 / 本条播不了 | **始终显示**，不计时 | 这些状态本身就是"用户需要看到的信息" |
| 离开页签 / 页面销毁 | 清掉计时器 | 不在后台空转定时器 |

「隐藏时第一下只唤出」的判据必须用**抬手那一刻**的 `wasHidden`，由 `onCardTouch` 在
唤出之前采集后传进 `handleTapUp` —— 单击是延后 380ms 执行的，到那时控件早被唤出了，
再读 `chromeVisible` 会**永远为 false**。

> 这个坑真的踩过：`onCardTouch` 无条件先调 `revealChrome(true)`，
> 而 `togglePause()` 里又写了一道 `if (!chromeVisible) { 只唤出; return; }` ——
> 那道判断永远不成立，于是"隐藏时点一下"照旧暂停。
> 表现与预期正好相反。修复方式是把判断上移到 `handleTapUp`、并改用 `wasHidden`，
> `togglePause()` 只负责切播放状态（不再自己判控件显隐）。

实现要点：隐藏用 `if (this.chromeVisible)` 而**不是** `opacity(0)` —— 透明度为 0 的按钮
**仍然可点**，"藏起来却还吃触摸"是最难查的一类 bug（本页在浮层上已经踩过一次）。
显隐带 `TransitionEffect.OPACITY`（220ms）淡入淡出。

**设备实测（模拟器，日志 + 布局双判据）**

| 步骤 | 结果 |
|---|---|
| 进入「视频」页约 8 秒 | `chrome hidden（播放中自动隐藏）`；`dumpLayout` 里工具行与操作栏节点消失 |
| 单击画面（控件隐藏时） | `chrome shown（交互唤出）` + `singleTap → 只唤出控件（控件原为隐藏）`；**时间读数持续推进**（未被暂停） |
| 紧接着再单击（控件已可见） | `singleTap paused=0` → 暂停，时间读数停住（连续两次读数不变） |
| 暂停 7 秒 | 控件仍在（暂停不计时） |
| 再单击 | `singleTap paused=1` → 继续，时间恢复推进 |
| 继续 4 秒后 | `chrome hidden` 再次出现 → 自动隐藏恢复生效 |
| 控件隐藏时双击两侧 | `doubleTap forward=1` + `seekHint`，**不暂停**（时间继续推进且跳了 10 秒） |

## 十、已知限制 / 待验证

- **页内软解**（硬解不支持的条目自动改走 FFmpeg）已实现并设备验证过；
  本页 XComponent **不带 `libraryname`**（软解桥是全进程单例，挂上会与播放页争抢桥状态），
  走 `surfaceId` 路径。
- 短视频页目前**不接 AVSession**（系统媒体控件由播放页负责），多端媒体键行为只在播放页保证。
- **不做无限循环**：末尾给「换一批」，避免"永远刷不完"的假象。
- 环境背景是**同一张封面**的放大压暗版，不是实时画面模糊（无模糊处理的性能开销）；
  后续若要"实时模糊"，需要评估模拟器软渲染下的开销。
- 「这批已经看完了」也可能出现在**追加请求失败**时（弱网）：此时点「换一批」即可重试。
- **强杀进程会留下服务端残留会话**：`aa force-stop`（安装覆盖、任务管理器杀进程）不会触发
  `onDestroy`，也就不会补发 `reportPlaybackStopped`，服务端会把这台设备显示为"仍在播放"
  直到它自己的空闲回收。正常返回/切页签/切条目都会补发（同一次运行内实测只更新同一个会话，
  不产生新会话）。彻底修法是在下次启动时比对 `/Sessions` 做一次清理，属后续增强。
- **清晰度是"请求播放地址时"的参数**：改档位只对**下一条**生效（设置页的 toast 已如实提示）。
- 模拟器上 `uitest uiInput doubleClick` 注入的两次点按间隔约 304ms，因此双击判定窗口定为
  350ms、单击延后 380ms 执行；真机上人手的双击更快，同样落在窗口内。
- **方向**在「视频」页签内是窗口级状态：离开页签会还原成"进来之前的方向"、回来时重新应用
  （见第六节）。真机的传感器旋转（`auto` 档配合机身姿态）尚未在实机复验 ——
  模拟器只能验"显式横屏 / 竖屏"这条路径。
- 横屏只做了"一屏一条 + 右下横排操作栏"这一版；若后续要做"横屏左右分栏（画面 + 信息侧栏）"，
  需要先确认目标机型的最小宽度。
- **主动全屏不持久化，且全屏中不能切页签**：页签栏收起后它就是唯一入口，因此离开页签一律收回全屏；
  要换页签得先退出全屏（点画面唤出控件 → 点全屏按钮）。这是"铺满"的必然代价，不做隐藏手势去兼顾。
- 主动全屏的**方向固定为横屏**（本机口径）。竖片在横屏下按"适应"缩放会更小 —— 这是短视频里
  "横屏看画面更大"的取舍（见第七节）；若将来要"全屏但保持竖屏"，只需把 `enterFullscreen`
  里的 `orientation = 'landscape'` 换成"保持原方向"。
- 全屏的**让位高度恒为 0**（沉浸式下系统把避让区尺寸清零，见第七节的探针结论）：
  真机若报出真实高度会自动让开，但本机无法验证这条路径。
- 真机手势导航下"全屏 → 从屏幕底部上滑"是否会与系统的返回手势冲突，模拟器上验不了。
