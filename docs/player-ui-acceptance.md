# 播放页验收清单（播放 / 渲染 / 美化）

本文件用于**人工快速验收**播放页改动。分三部分：
① 已由设备实测确认的项（附证据）；② 需要人工目视/触控确认的项；
③ 已知限制与临时诊断件。

手动验收约需 **2–3 分钟**：播放任意视频后逐条对照即可。

### 本轮（全屏观看：沉浸式 + 横屏）：真机实测证据

真机 HUAWEI HBN-AL00（1260×2844，density≈3.39），条目标题「【走进地狱】养鬼吃人…」（16:9）。

| 项 | 证据 |
|---|---|
| 进入播放页即沉浸式全屏 | dumpLayout 对照：首页有系统状态栏节点 `(630,64) 1260×128`；**播放页无该节点**，根容器 `1260×2844` 满屏 —— 状态栏与导航栏已隐藏（`setWindowSystemBarEnable([])`） |
| 控件层避让挖孔/状态栏 | 顶部栏按钮实测 `(121,148) 162×162`，未贴屏幕最顶端（y 从 148 起），即控件按 insets 内缩、视频层仍铺满 |
| 横屏全屏可切换 | 点底部「方向」按钮后 dumpLayout 根容器 `1260×2844` → **`2844×1260`**；按钮文案 `跟随系统`→`横屏`；底部工具行由 4 个扩为 5 个（适应/横屏/音频字幕/1x/软解） |
| 横屏上屏缓冲几何 | `hidumper -s RenderService -a surface` → `jellyfin_playerSurface` 的 `default-size=[2844x1260]`、`transformType=1 <rotation by 90 degrees>`，即渲染面确已按横屏输出 |
| 横屏画面按比例铺满 | dumpLayout 视频面节点由竖屏 `1259×709` 变为 **`2241×1259`**（2844×1260 屏内 16:9 等比适配的精确值）；截图像素分析：内容列 x 304..2540（宽 2236）、内容行 y 0..1256（高 1256），仅左右各约 300px 为该比例模式下的等比留黑 |
| 横屏下「比例」仍生效 | 横屏点「比例」：视频面 `2241×1259` → **`2844×1260`**（填充铺满），按钮文案 `适应`→`填充` |
| 横屏下轨道面板可用 | 横屏点「音频/字幕」：面板正常展开，含「音频 / 字幕」标题、「关闭」、「关闭字幕」、「该视频没有字幕」 |
| 退出播放页恢复 | 点返回后回到详情页（`1260×2844`），**系统状态栏节点 `(630,64) 1260×128` 重新出现**，窗口方向恢复竖屏 |
| 切回竖屏 | 再点「方向」：根容器 `2844×1260` → `1260×2844`，视频面按竖屏重算 |
| ±10s 按钮精确性（横/竖屏） | 横屏实测 `-10.47s / -10.29s / -10.48s / -10.89s`；竖屏实测 `-10.48s / -10.89s`（`0:xx` 文案与进度值双重核对） |

> 本轮修复的两处缺陷（均为设备实测发现，不是推测）：
> 1. **横屏时视频面几何不重算**：`areaWidthVp/areaHeightVp` 原是普通字段，
>    ArkUI 不会因它们变化而重新执行 XComponent 的宽高更新闭包 —— 横屏后视频面仍停在竖屏算出的
>    `371×209vp`，画面缩在屏幕中间、两侧大片黑边。改为 `@State` 后横屏几何正确。
> 2. **横屏时手势左右分区错误**：`getScreenWidth()` 取的是 `display.width`，而设备实测
>    **该值不随窗口旋转变化**（横屏时仍为 1260px ≈ 371vp，而触摸 x 最大约 839vp）。
>    后果是横屏下整个屏幕都被判成「左侧」（纵滑会去调亮度而非音量），
>    且双击的「两次抬手横向距离 < 屏宽/3」阈值也缩水成约 124vp。
>    新增 `gestureWidth()` 改用随旋转更新的根容器实测宽度。

### 本轮（修复「软解黑屏」）：设备实测证据

**现象**：硬解不支持的编码（如 HEVC）自动回退 FFmpeg 软解后，画面**全黑**；界面上只有
「已自动切换软解播放」，没有报错，进度还在走 —— 看起来"在播，但什么都看不见"。

**根因**：EGL 上下文是在**原生工作线程**上初始化的（`softPlayOpen` 走 `RunAsync`），
而逐帧渲染发生在 **ArkTS UI 线程**（`softPlayRenderLast` 是同步接口）。
EGL/DGLES 把"当前上下文 / 当前 surface"记在**线程私有**状态里，于是 UI 线程
每一次 `eglSwapBuffers` 都失败 —— 帧解出来了、帧号在涨，但一个像素都上不了屏。

实测环境：模拟器 `127.0.0.1:5555`，条目「山中传奇」（1920×816 HEVC，硬解报
`5400106 VID_DEC_ERR-video/hevc-unsupport … unsupport video decoder type` → 自动回退软解）。

| 项 | 证据 |
|---|---|
| 修复前：EGL 在**工作线程**初始化 | `DGLES: Initialize display` 所在 tid = **31744**（`RunAsync` 工作线程） |
| 修复前：逐帧 swap **全部失败** | tid = **31628**（UI 线程）每约 70ms 一条 `DGLES: EGL_BAD_SURFACE, g_handle is null`（0x300d）；单次播放累计 **17126 条** |
| 修复前：上层毫无察觉 | 帧号正常增长、进度正常上报；屏幕上只有「已自动切换软解播放」（上屏错误被这条提示**盖掉**） |
| 修复后：同线程初始化 | `SoftPlay: softPlayInitRenderer ready=1 reused=0 mode=xcomponent geo=1259x537 tid=12720`（该 tid = UI 线程） |
| 修复后：swap 不再失败 | 整场 `EGL_BAD_SURFACE` 计数 **0**（修复前 17126） |
| 修复后：首帧即刻上屏 | `softPlayNextFrame #1 pts=2021.603 decodeMs=256` → `softPlayRenderLast ok #1`（起播后约 **0.5s**） |
| 修复后：画面确实在动（像素实测） | 视频条带逐次采样：平均亮度 **22–48**、亮像素占比 **70–86%**、**帧间差 8–40**（静止/黑屏时该值为 0，修复前恒为 0.00） |
| 修复后：重进播放页（surface 重建）也能出画面 | `OnSurfaceDestroyed` → 新 `OnSurfaceCreated window=…2B20D30` → `softPlayInitRenderer … reused=0`：**按新 window 重新初始化**，不再画到已销毁的显示面 |
| 修复后：续播跳转生效 | `softPlaySeek queued target=2054.844s` → `seek applied to=2054.844s frame=#1`，首帧 pts=2045.96（跳到目标前一个关键帧） |

同轮一并修掉的三处"静默失败"（都属于同一类缺陷：异常没有到达用户/日志）：

1. `EglRenderer::destroy()` 不再销毁 **framework 持有的 XComponent window**（只销毁自己用
   `OH_NativeWindow_CreateNativeWindowFromSurfaceId` 创建的）；误销毁会毁掉显示面，
   之后在同一 XComponent 上重建 EGL surface 便再也不上屏。
2. 渲染器↔surface 的绑定按 **window 指针**校验（`boundToWindow()`），并在帧循环里就地重建 ——
   杜绝"复用了已销毁 surface 的渲染器"（同样是黑屏，且不报错）。
3. `drawFrame()` 显式检查**线程一致性**与 `eglMakeCurrent` 的返回值（此前返回值被忽略，
   于是"上下文没绑上"被当成"绘制成功"）。上屏失败不再被吞：连续 3 帧失败即停止软解、
   进入错误态并给出「重试」入口。

> 模拟器性能提示（非缺陷）：x86 模拟器软件 HEVC 解码约 **5–6 fps**（片源 24fps），
> 因此软解在模拟器上是"慢放"；真机（HUAWEI HBN-AL00）此前实测约 10fps（4K HEVC）。

## 一·补2 底部工具行布局（已实测）

修复前：5 个按钮横排放在 `Scroll` 里，实测需约 **390vp**，而竖屏可用宽度只有约 **340vp**
（屏宽 371vp − 左右各 16vp 内边距）⇒「倍速」被裁（dump bounds `1101–1206`）、
「软解」整块落到屏幕外（节点树里都没有）—— 用户无法手动进入软解。

修复：改为 `Flex({ wrap: Wrap, justifyContent: Center })`，每个按钮 `margin({ left/right: 4, top: 4 })`。
一行放不下就换行并保持居中，**不做两套横竖屏布局**（避免行为分叉）。

| 方向 | 实测（dump 取按钮 bounds） |
|---|---|
| 竖屏 1260×2844 | 两行：`y=2485` 适应 / 跟随系统 / 音频·字幕；`y=2660` 1x / 软解 —— 5 个按钮全部完整在屏内 |
| 横屏 2844×1260 | 一行（`y=1076`）：适应 / 横屏 / 音频·字幕 / 1x / 软解 —— 全部完整在屏内 |

> 短视频模式的入口与行为单独成文：见 `docs/short-video-mode.md`（含设备实测表）。

## 一·补3 控制面板撤离与锁定语义（部分待复验）

需求：① 视频控制面板可以点击非功能区域撤离；② 屏幕锁定只能通过点击锁的位置恢复，
锁模式单击显示锁、再次点击锁取消锁定。

| 项 | 状态 | 证据 / 说明 |
|---|---|---|
| 面板空白区点击即撤离 | ✅ 实测 | 唤出面板 → 点顶栏与中央控制簇之间的空白（`630,640`）→ 面板收起 |
| 锁定后无整屏遮罩 | ✅ 实测 | 原实现是 85% 黑幕 + "点击任意位置解锁"，点画面任意位置都会解锁 |
| 锁定态单击只显示锁、不解锁 | ✅ 实测 | 单击后锁提示出现、控制面板保持隐藏 |
| 点锁图标解锁 | ✅ 实测 | 点锁提示上方 70px 处的锁图标 → 解锁并唤出控制面板 |
| 锁定后**默认不显示**锁提示 | ⏳ 待复验 | 渲染条件曾只判 `controlsLocked`（锁一按下提示就常驻），已改为 `controlsLocked && lockBadgeVisible` |
| 点锁提示之外收起提示且仍锁定 | ⏳ 待复验 | 锁提示改为**不铺满整屏**，避免与手势状态机对同一次点击各处理一遍 |

实现要点（两个必须知道的坑）：

1. **播放页有两条输入通道**：ArkUI 手势层（透明层 `onTouch`）与原生 XComponent 兜底轮询
   （`startTouchPollTimer` → `handleNativeTouch*`，两者都带 `controlsLocked` 守卫）。
   点"锁定"按钮的同一次抬手还会被视频区手势状态机看到 ⇒ 需要 `kLockGraceMs = 450`
   （大于单击判定延时 `kSingleTapDelayMs = 260`）的宽限期把这次点击吃掉，
   否则"点锁定"会立刻被判成"单击 → 显示锁"。
2. **锁提示只在需要时渲染**：`LockBadge` 必须同时判 `lockBadgeVisible`。
   该缺陷是先用**临时 hilog 打点**定位的：日志显示 `singleTap locked=true` 从未出现、
   而锁提示却在节点树上 ⇒ 说明它不是单击触发的，而是渲染条件漏判（诊断代码已移除）。

### 2. 软解解码提速（PR #22）

同一 HEVC 条目（1920×816，真机/模拟器同源）前后对比，日志口径为
`softPlayOpen … decodeThreads=` 与逐帧 `… decodeMs= … fps= …`：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 解码器线程数 | 1（FFmpeg 默认单线程） | **5**（`thread_count = 0` 自动按核数） |
| 单帧解码耗时 | 46–90ms | 31–38ms |
| 实际帧率（首帧起算） | ≈5.6fps（100 帧 / 17.7s） | **≈8fps（100 帧 / 12s）** |

> 口径说明：均为同一模拟器、同一条目、同一取流路径；`fps` 由"首帧起算的帧数 / 墙钟"计算
> （不是片源帧率），因此可直接横向对比。片源 24fps，模拟器仍非实时（软件解码），
> 但单帧耗时下降约 **40%**、帧率提升约 **43%**。

## 二、需要人工确认（我做不了，自动化手段在此失效）

### 1. 音轨切换的"听感"
- **操作**：播放「阴阳路4：与鬼同行」→ 控制条「音频/字幕」→ 点「国语」→ 再点「粤语」
- **预期**：对白语言随之切换（粤语 ↔ 国语），画面不中断、进度不跳
- **为什么需要人工**：自动化只能证明**播放器的轨道选中状态变了**（探针 + `getSelectedTracks`），
  听不出声音；设备侧也没有可回读的音频输出。

### 2. 视频区手势的观感
- **操作**：播放页 → 视频区横向滑动（seek）、左侧纵向滑动（亮度）、右侧纵向滑动（音量）、按住 0.6s（2× 快进）
- **预期**：出现带图标与数值的胶囊状反馈浮层；横向滑动松手后进度跳变
- **为什么需要人工**：浮层样式属观感判断（识别逻辑本身已由探针验证）。
- **已修缺陷（曾记录在此处）**：手势原按"每次 Move 事件的位移"判方向、阈值 5px，
  慢速滑动（每次事件位移 ≤5px）会被整段过滤、完全不响应。
  改为用**相对按下点的累计位移**判方向与幅度后，设备实测：
  500ms 滑完 500px 的**慢速**滑动 `seekDeltaMs=294.5`（修复前为 0）；
  右侧纵向下滑 `volume` 由 `1.00` 变为 `0.29`；点击视频区仍能正常显隐控制条。
  （注：`uitest` 注入的 swipe 本身有一定丢包率，同一手势重试即复现，不是应用问题。）

### 3. 加载态观感
- **操作**：连播多个视频，注意"打开播放器"的瞬间
- **预期**：显示「影片标题 + 类型 + 转圈 + `正在加载 · <播放器状态>`」，而不是空白黑屏
- **为什么需要人工**：该状态通常 <1 秒，抓取周期跟不上

### 4. 整体观感
- 请指出最不满意的 1–2 处（间距/字号/配色/层级），我优先修。

### 5. AVSession 媒体键反向控制（耳机按键 / 系统媒体控件）
- **操作**：播放中按耳机播放/暂停键，或用系统媒体控件（通知栏/锁屏）暂停
- **预期**：播放器暂停/恢复（已订阅 `play/pause/stop/seek` 并映射到本页控制）
- **为什么需要人工**：`uitest uiInput keyEvent 85`（媒体播放暂停键）**不会**触发 AVSession 的媒体键分发 ——

## 三、已知限制与临时诊断件

- **详情页"约 20 秒必崩"已修复**（Issue 性质：`__fd_chk` abort）。
  现象是打开详情页停留一会应用直接消失；根因是 OpenHarmony 的 `FD_SET`
  在 **fd ≥ 1024** 时经 `__fd_chk` **直接 abort**，而进程 fd 上限是 32768 ——
  详情页并发加载图片（每张图一个工作线程 + TCP 连接）越过 1024 就崩。
  已把 `select()`/`FD_SET` 全部换成 `poll()`。
  **原因、证据与实测见 `docs/detail-page-fd-abort.md`。**
- **软解模式下不能切换轨道**：软解会话只解码视频帧（无音频输出、无字幕解析），
  面板在这种情况下会明确提示"软解模式：轨道切换不可用"。
- **续播（含软解）已可用**：详情页按钮显示「继续播放 · mm:ss」（取服务端 `PlaybackPositionTicks`）。
  软解会话的 seek 改为**排队执行**（原生侧只记录目标，真正的 `av_seek_frame` 由下一次拉帧
  在解码线程上执行），因此软解下"从上次位置续播""拖动进度条""±10s"都生效；
  设备实测探针 `seekApplied to=16.3`，服务端进度 `pts=6.3` → `pts=21.1`。
  （本节此前写的"软解暂不支持从上次位置续播"**已作废**。）
- **硬解路径在本模拟器上无法实测**：模拟器对 1080p H.264 High 8-bit 报
  `5400103 VID_DEC_ERR ... video decode failed`，所有内容都会自动回退软解。
  因此「视频比例」的硬解分支（`AVPlayer.videoScaleType` = 适应/填充）与"硬解下切换比例
  是否会因视频面尺寸变化而重建 surface"这两点**只有编译级验证**，需在真机上复验。
  软解分支（`EglRenderer` 按模式换算顶点缩放 + 视频面尺寸）已设备实测。
- **软解播放已不再触发 appfreeze**：此前 `RangeCache` 的同步 HTTP 跑在 UI 线程上
  （faultlog 主线程栈可证），逐帧拉取时主线程被阻塞 6 秒以上。现在"后台预取 + 帧拉取异步 +
  UI 线程渲染"三层处理，实测连续 70 秒软解播放：`0:28 · 第 842 帧 · EGL 已渲染 · 已上报进度`，
  无新增 appfreeze。注意 **EGL 渲染必须留在 UI 线程**（工作线程 swap 返回 `0x12301`，上不了屏）。
- **轨道切换的两条路径**：优先用播放器自身的轨道切换（`getTrackDescription` + `selectTrack`，
  不打断播放）；播放器没有暴露可切换轨道时（转码等）才回退到
  "改写 `AudioStreamIndex`/`SubtitleStreamIndex` → 重新取流 → seek 回原位"。
  **回退路径尚未在设备上触发过**（该条目上播放器总能给出轨道列表），只有编译验证。
- **软解渲染分辨率（已修复，无需 640 上限）**：渲染缓冲几何不再写死 640 宽，
  改为按「源尺寸 ∩ XComponent 像素尺寸」协商（`EglRenderer::queryRenderGeometry`），
  并在 `eglSwapBuffers` 失败时**逐级折半降级**（最多 4 步、下限 320x180）重试；
  协商结果经 `SoftPlayOpen` 的 `renderWidth`/`renderHeight` 回传，宿主据此决定解码宽度
  （`softDecodeMaxWidth`，0 表示按源分辨率）。这样真机拿到全分辨率、模拟器自动落到它能吃下的档位，
  不再靠"预先写死一个小上限"牺牲画质。
- **调试显示与临时诊断件（已全部移除）**：播放页原有的常驻诊断行（帧号 / 抓取字节 / EGL 状态 /
  锁定与控制条状态）、6 个 `player_*.txt` 探针、软解自动截图导出（`softcapture_*` / `softrender_*`）
  与底部「存帧」按钮均已移除；`native/feature/player/xcomponent_bridge.cpp` 触摸热路径上的
  逐事件 hilog 也已删除。
  代码里保留的 `softStatus` 只是**用户可见提示**（打开中/超时/失败/已自动切换软解），
  普通提示 4 秒自动隐去，避免长期压在画面上。
  **本轮又清掉了最后一处调试 UI**：详情页「播放选项」里的「软解首帧预览」（那是一个开发者工具：
  它把 FFmpeg 探测结果与首帧 PNG 直接摊在界面上），连同 ArkTS 侧的
  `playerSoftDecodeProbe` / `softPlaySelfTest` / `softPlayDumpFrame` / `renderTargetProbe`
  四个包装器与类型声明一起删除。
  原生实现仍保留在 `native/napi/jellyfin_napi.cpp`（作为**换机型/换 XComponent 类型时的判定工具**），
  但**界面上不再有任何入口**；发布前的 FFmpeg 门禁改由 `scripts/verify_hap_ffmpeg.sh`
  （包内 DT_NEEDED 依赖闭包校验）承担，不再依赖界面操作。
- **服务端会话堆积**：`/Sessions` 曾达 60+ 条（多为我反复登录/安装的测试痕迹）；
  已在 `EntryAbility.onDestroy` 加"退出时上报停止"的兜底（仅编译验证，`aa force-stop` 不走生命周期回调）。
